# 规则配置 / 统计分析 前后端联调问题记录

> 阶段：第七阶段 Backend Demo（规则配置中心 + 统计分析）
> 范围：仅记录当前 Demo 为快速跑通而做的过渡处理、字段 / 状态 / 口径差异，以及后续正式领域设计需要统一解决的问题。本阶段不做最终领域模型、规则引擎、数据仓库改造。

## 1. Rule 版本与 Fence 版本的关系

| 项 | 当前 Demo 处理 | 影响 | 正式领域设计建议 |
|---|---|---|---|
| 规则版本 `v3.x` 与围栏版本 `v3.x` | 各自维护独立版本号（`DemoRule.version` / `DemoFence.version`），编号空间相互独立，仅靠 `params` / 描述里出现的围栏名做弱关联 | 同一条“人员进入动态禁区”业务，规则版本与围栏版本可能不一致，前端无法从规则直接定位到具体围栏版本快照 | 建立 Rule ↔ Fence 的显式关联（ruleId / fenceId / version 三元组），规则引用某一**已发布快照**版本的围栏，发布时校验二者均已生效 |
| EDGE 同步状态 | Rule 与 Fence 各自模拟 EDGE-01~04 同步结果，互不通告 | 可能出现“规则已同步、围栏未同步”的边缘状态，Demo 不做联合校验 | 边缘端应以“策略包（规则+围栏+阈值）”为最小下发与对账单位，统一版本指纹 |

## 2. Rule 参数与 Collision 当前阈值的关系

- 碰撞距离阈值（安全 10m / 严重 6m / 紧急 3m）目前仍写在 `CollisionService` 的 Demo 判定逻辑与 `RuleService.simulate` 的仿真逻辑两处，**没有**让实时判定在运行时读取 `RuleRepository`。
- 原因：任务书明确“规则页面真实后端化，但不重写前几阶段实时判定，避免一次重构过大”。
- 影响：在规则页面修改“预警距离”并发布后，`/devices` 的实时碰撞风险等级不会随之改变（仿真对话框会变，真实判定不变）。
- 建议：正式实现时由 `CollisionService` 在判定时读取当前**已生效**的设备规则参数（带缓存与版本号），规则发布后刷新判定参数，并保留参数变更审计。

## 3. Rule 与 AI 阈值的关系

- AI 置信度阈值（85%）、连续帧、持续时间等同样存在两份：AI 模块 Demo 判定逻辑与 AI 类规则参数。
- 当前 AI 事件由前序阶段的 AI 模块产生，规则页面只做参数展示 / 仿真 / 生命周期管理，不反向驱动 AI 复核阈值。
- 建议：统一为“识别策略”由规则中心下发，AI 服务加载生效版本；模型版本（PPE-Detection-v2.4.1）与规则版本分别管理、互相引用。

## 4. 风险等级差异

- 全系统统一四级：`一般 / 预警 / 严重 / 紧急`（Rule、Alert、Analytics 已对齐）。
- 历史遗留：早期部分 Mock 使用“高风险 / 中风险”等口语化表述；本阶段统计聚合通过 `RiskClassifier.isHighRisk`（严重+紧急=高风险）统一“高风险”口径。
- 建议：正式领域模型固化等级枚举与数值权重（用于排序、SLA、升级），各模块只引用同一枚举，禁止散落字符串。

## 5. Analytics 事件分类口径（重点）

- **问题**：前端统计图表使用归并大类（人员越界 / 设备距离风险 / 未佩戴安全帽 / 人员异常 / 翻越护栏 / 视频设备异常 / 设备异常），而后端 `DemoAlert.eventType` 是细分名（危险区域闯入、设备接近预警、人员滞留、设备交汇风险、机械设备异常……）。
- **当前处理**：新增统一分类器 `projection/shared/RiskClassifier.analyticsType`，把细分 eventType 归并到分析大类；统计 KPI/分布/排行/设备/人员全部走该分类器，避免三套分类。
- **遗留**：首页 `SafetyProjectionService.riskDistribution` 目前仍按原始 `eventType` 细分名输出（为不破坏首页既有测试与展示），与统计页大类口径不完全一致。
- 建议：正式阶段让首页 / 大屏 / 统计共用同一“事件分类字典 + 归并规则”，废弃前端常量 `ANALYTICS_TYPES` 与后端硬编码 switch。

## 6. 班组（Team）数据来源

- `DemoAlert` 没有 team 字段，只有 `assignee`（责任人）与 `target`（对象）。
- 当前 `RiskClassifier.teamOf` 用 **Demo 映射**：按人员编号段 / 设备编号 / 责任人推断班组（装卸一班、装卸二班、设备保障班、安全管理班、外协单位）。
- 影响：班组处置效率为近似值；人员调班后无法自动反映。
- 建议：正式模型补齐“人员-班组-班次”主数据，告警 / 处置记录冗余 team 字段或关联查询。

## 7. 响应 / 关闭时间口径

- **平均响应时间**：`occurredAt → Timeline 中首个文本含“确认”节点` 的平均秒数。
- **平均到场时间**（班组效率）：`occurredAt → 首个含“接单/到场/到达现场/赶赴”节点`。
- **平均关闭时间**：`occurredAt → 首个含“关闭”节点`。
- 任一事件缺少对应节点则**跳过该事件**（不计入平均，返回 `null`，前端展示 `--`），不编造时间。
- 局限：依赖 Timeline 文本关键字匹配，正式实现应改为结构化的阶段时间戳（confirmedAt / arrivedAt / closedAt）。

## 8. 重复风险定义

- “重复风险事件”= 按 `target`（同一对象，如同一人员 / 同一设备）分组，出现次数 ≥ 2 的组所包含的事件总数。
- “重复风险人员 / 高频设备”同理按人员编号 / 设备编号聚合。
- 局限：以对象文本提取编号（正则 `P-\d+` / `[A-Z-]+-\d+`），未与人员 / 设备主数据外键关联；正式实现应使用稳定对象 ID。

## 9. Demo RiskScore

- 区域风险排行 `score = total + 2 × highRiskCount`，代码中已注释 `DEMO RISK SCORE`，仅用于排行排序，**不是**正式风险评估模型（不考虑权重衰减、事件时效、区域暴露度等）。

## 10. 趋势基线（trend DEMO baseline）

- InMemory 种子集中在 2026-09-04，缺少长期历史时序。为让“本周 / 本月”曲线可读：历史桶叠加确定性 DEMO 基线（本周固定数组、本月取模序列），**当天桶永远只统计真实数据**；响应中以 `trendDemoBaseline=true` 与逐点 `demoBaseline` 标记。
- KPI、风险类型、区域、设备、人员等板块**不叠加任何基线**，全部为真实聚合。
- 建议：正式阶段由 openGemini / 事件库提供真实历史时序后移除基线。

## 11. 统计明细分页

- 后端 `GET /analytics/events` 已支持 `page/pageSize` 真实分页；当前前端 `EventDetailTable` 组件无分页器，Demo 阶段以 `pageSize=200` 一次拉取展示。
- 建议：正式阶段为明细表格加分页器并改为按页请求。

## 12. simulate-surge 的实现方式

- “风险突增”不是返回另一套假数组，而是向 `AlertRepository` 注入一组固定前缀 `ALM-SURGE-` 的演示告警（area=装卸区 A、source=人员安全），并逐条广播 `alert.new`，因此首页 / 大屏 / 统计同时变化；恢复时按前缀删除。重复开启做了幂等保护（已存在则不重复注入）。
- 局限：进程内存数据，重启回到种子（Backend Demo 预期行为）。

## 13. 规则写操作与实时事件

- 规则生命周期动作（提交 / 批准 / 发布 / 重下发 / 回滚 / 停用 / 版本异常）成功后广播 `rule.changed / rule.published / rule.sync.changed`，消息体只含 `ruleId/version/status/synced/total` 等轻量字段，前端收到后 REST 重拉，不通过 WS 传完整规则对象。
