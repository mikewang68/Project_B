## 更新顺序

1. 核对本系统代码版本、数据库迁移历史和配置，备份应用及受保护配置。
2. 合并源码及依赖，按模块说明构建；在实验室环境执行针对性检查。
3. 核对数据库库名/schema、列及约束后补缺失迁移。已有列不重复执行；不在现有库重跑初始化、演示种子或重置脚本。
4. 配置独立 SSO 受众凭据、可信入口、原生主体及资源映射。确认系统支持 V2 后再启用对应身份。
5. 发布自己的后端和前端，验证登录、允许的业务动作、跨范围拒绝、只读限制和撤权，记录采用的提交号。

## 对接原则

- `project_id / region_id / subsystem_code` 来自可信服务端上下文，不能接受客户端自行指定的归属。
- 现有公司、仓库、货主或组织约束继续执行，与中央范围求交。
- `my_info` 用于本系统范围，`my_project_zone_info` 只用于已登记共享资源；二者都有参数化形式。原查询的 `OR` 必须括起来再追加范围条件。
- 详情、统计、导出、写入与列表使用同样的范围和动作检查；前端按钮状态不能替代服务端校验。
- 新账号的中央授权与原生资源就绪必须同时满足。无法证明历史归属时保留未分配状态，不批量赋予正常区域。
- 后台任务、机器上报及真实设备来源仍须单独登记可信身份和范围，不借用平台管理员或浏览器会话。

源码更新由各负责人在自己的版本中合并、构建和发布。业务算法、现场设备映射和新区域资源按各系统实际事实补齐。登录凭据及现场配置通过原有私有渠道交接。
