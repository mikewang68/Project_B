# IAM / SYS 本周自查与规则智能体改进

> 周期：2026-09-30 当周
> 范围：IAM（统一身份与权限）、SYS（系统设置与维护）
> 主线：在不引入任何外部大模型、零 API 成本、完全离线可运行的前提下，把权限治理与日志诊断做成**基于真实数据 + 确定性规则引擎 + 结构化诊断 + 可解释结果 + Human-in-the-loop** 的能力。

---

## 42.1 当前系统自查

### IAM（统一身份与权限）

**现状**

- 已具备完整的用户、角色、权限（SYSTEM / MENU / BUTTON 三级）模型，以及用户—角色、角色—权限关系。
- 登录、鉴权、用户 CRUD、角色 CRUD、权限分配、菜单树等基础能力闭环；操作有日志记录。
- 权限在后端按 `permissionCode` 强制校验，前端按权限码控制菜单与按钮。

**短板**

- 一个用户通过多角色叠加后**最终拥有哪些权限、每个权限来自哪个角色**，管理员无法直观看清，只能人工逐角色核对。
- 权限体系缺少"体检"能力：无成员角色、未被引用的权限、只读角色混入写权限、角色权限重叠/重复等问题无法被主动发现。
- 权限关系对管理员不直观，是最容易"看起来只是普通 CRUD"的地方。

**改进**

- 新增**有效权限视图与来源解释**：实时计算用户的最终权限，并标注每个权限的来源角色；支持对单个权限做"为什么拥有 / 为什么没有"的解释。
- 新增 **IAM Permission Health Agent**：用确定性规则对全量权限关系做健康诊断，输出结构化、可解释、可验证的发现。
- 架构层新增 **AiProvider 扩展点**，默认 Disabled，为未来无侵入接入大模型做准备。

### SYS（系统设置与维护）

**现状**

- 已具备操作/登录日志、数据字典、系统配置等能力；日志记录用户、模块、动作、对象、详情、IP、结果、耗时等字段。
- 支持日志分页查询与 CSV 导出。

**短板**

- 日志只能**被动逐条查询**，缺少概览：一段时间内成功/失败多少、失败率多高、集中在哪些模块和用户，管理员无法快速掌握。
- 缺少诊断能力：高失败率、连续权限拒绝、模块/用户失败集中、短时间重复失败等现象无法被主动识别。

**改进**

- 新增**日志统计接口**：按时间范围/模块/用户/结果聚合，输出总量、成功、失败、失败率及模块、用户、结果分布。
- 新增 **SYS Log Diagnosis Agent**：用确定性规则对日志做诊断，输出结构化发现，并可下钻到证据日志。
- 同样新增 **AiProvider 扩展点**，默认 Disabled。

## 42.2 本周普通优化（高价值、低风险）

| 模块 | 优化 | 说明 |
| --- | --- | --- |
| IAM | 有效权限与来源解释 | 基于 `iam_user_role` / `iam_role` / `iam_role_permission` / `iam_permission` 真实关系，批量查询、无 N+1，实时计算用户最终权限及每个权限的来源角色；支持单个权限的拥有/缺失解释。 |

## 42.3 本周智能体（规则驱动）

### IAM Permission Health Agent（权限健康诊断）

**数据来源**

- 真实表关系：`iam_user`、`iam_role`、`iam_permission`、`iam_user_role`、`iam_role_permission`。
- 仅对 `BUTTON` 叶子权限做检测，天然排除 SYSTEM / MENU 父节点，避免误报；只统计真实存在的用户与角色，忽略指向已删除对象的孤儿关系。

**规则**

| 规则 | 类型 | 级别 | 含义 |
| --- | --- | --- | --- |
| IAM-001 | EMPTY_ROLE | LOW | 启用状态的角色没有任何成员。 |
| IAM-002 | UNUSED_PERMISSION | LOW | 某叶子权限未被任何角色引用。 |
| IAM-003 | OVERLAPPING_ROLE | LOW | 同一用户的两个角色，其中一个权限是另一个的严格子集，对该用户可能冗余。 |
| IAM-004 | HIGH_RISK_PERMISSION | LOW | 高风险权限（删除 / 权限 / 角色 / 用户 / 配置修改类）盘点，标注来源角色。 |
| IAM-005 | READ_ONLY_CONFLICT | HIGH | 命名呈只读语义的角色包含写权限（add / edit / delete）。 |
| IAM-006 | DUPLICATE_ROLE | LOW | 同一用户的两个角色权限集合完全相同。 |

**输出**

- 概览：角色数、权限数、用户数、发现数及 HIGH / MEDIUM / LOW 计数。
- 发现列表：每条含规则 ID、级别、类型、标题、说明、证据与处理建议。

**证据**

- 每条发现都带具体证据（角色编码、权限编码、用户名等），可逐条核对，不是笼统结论。

**作用**

- 让管理员主动发现权限体系中的冗余、冲突与遗留配置；**只产出分析与建议，不执行任何写操作**，是否调整由人工确认（Human-in-the-loop）。

### SYS Log Diagnosis Agent（操作日志诊断）

**数据来源**

- 真实表 `sys_operation_log`，按时间范围（默认近 7 天，最长 30 天）与模块 / 用户 / 结果过滤取明细。

**规则**

| 规则 | 级别 | 含义 |
| --- | --- | --- |
| SYS-LOG-001 | HIGH | 整体失败率 ≥ 20% 且总操作数 ≥ 10。 |
| SYS-LOG-002 | MEDIUM | 同一用户在 10 分钟窗口内出现 ≥ 3 次 403 / 权限拒绝，可能存在权限配置问题。 |
| SYS-LOG-003 | MEDIUM | 某模块失败数占全部失败 ≥ 60% 且达到最低数量，失败集中于该模块。 |
| SYS-LOG-004 | MEDIUM | 某用户失败数占比 ≥ 50% 且达到最低数量，为当前失败事件主要来源。 |
| SYS-LOG-005 | LOW | 同一 用户+模块+动作+结果 在 2 分钟窗口内大量重复，**可能**是重复点击、错误重试、前端循环请求或权限配置问题（只说"可能"，不武断根因）。 |
| SYS-LOG-006 | INFO | 无失败时不强行制造异常，输出"当前时间范围未发现明显异常"。 |

**输出**

- 时间范围、汇总（总数 / 成功 / 失败 / 失败率）与发现列表。

**证据**

- 每条发现带 `evidenceLogIds`，前端可点击"查看证据日志"，列表自动定位到对应日志，下钻核对。

**作用**

- 把日志从"被动查询"升级为"主动概览 + 可解释诊断"，帮助管理员快速定位失败来源；同样**只给建议、不自动处置**。

## 43. 为什么当前不接大模型

> 当前阶段优先采用规则驱动方案，原因包括**零成本、结果确定、可解释、离线可用、便于测试**，并可避免模型幻觉直接影响权限管理和运维判断。

权限管理与运维诊断要求结论稳定、可追溯、可复核。规则引擎对同一组数据永远给出相同结果，每条结论都能下钻到具体证据；若直接让大模型判断"权限是否合法""异常根因是什么"，可能因幻觉产生错误结论，且带来 API 成本与在线依赖。

同时需要说明：这不是"不接 AI"，而是**阶段性架构选择**。

> 已在架构层预留 `AiProvider`，后续可选择 DeepSeek 等 API 对规则结果进行自然语言增强。

## 44. 后续 DeepSeek 接入路线（只设计，不实现）

```text
Rule Engine（规则负责事实）
        ↓
Structured Findings（结构化发现 + 证据）
        ↓
DeepSeekAiProvider
        ↓
自然语言解释 / 复杂问答（LLM 负责解释）
```

原则：**规则负责事实，LLM 负责解释**。DeepSeek 不直接判断原始权限是否合法，而是在规则产出的结构化事实与证据之上做自然语言组织与表达。

未来新增一个 `DeepSeekAiProvider` 实现并配置 `app.ai.provider=deepseek` 即可，无需改动现有业务与规则代码，真正无侵入。
