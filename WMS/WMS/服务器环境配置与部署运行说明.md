# MT-WMS 服务器环境配置与部署运行说明

本文用于指导 `mt-wms-rebuild/WMS` 在 B 项目开发服务器上完成环境配置、openGauss 数据库连接、构建、部署、启动、验收、更新和故障排查。

适用环境：

| 项目 | B 项目服务器现状 | MT-WMS 要求 |
|---|---:|---:|
| 操作系统 | openEuler 24.03 LTS-SP3 x86_64 | 支持 |
| Java | 17.0.19 | Java 17 |
| Maven | 3.9.16 | Maven 3.9.x |
| Node.js | 24.18.0 | Node.js 24.x，至少 24.11.1 |
| pnpm | 10.34.5 | 10.34.5 至 11.x |
| 容器运行时 | iSulad 2.1.6 | 用于访问现有 openGauss 容器 |
| 数据库 | openGauss 6.0.5 | 支持 |
| 服务管理 | systemd | 支持 |

## 1. 推荐部署方式

推荐先把前后端一体化 JAR 部署到 `bpoc-node4`，直接连接该节点现有的 openGauss 容器：

```text
浏览器
  -> HTTPS / Easegress
  -> bpoc-node4:18080 / mt-wms.jar
  -> node4 上的 openGauss 6.0.5
```

Vue 前端会在 Maven 构建时编译并放入 JAR，因此服务器运行阶段不需要 Node.js，也不需要把前端复制到 node6 Nginx。Node.js 和 pnpm 只在构建阶段使用。

如果必须把应用放到 `bpoc-node5`，则需要让 node5 通过内网访问 node4 的 openGauss，并配置 openGauss 客户端访问规则和防火墙白名单。不要将数据库端口直接开放到公网。

## 2. 上传或检出项目

可以在服务器通过 Git 检出，也可以使用 `rsync` 上传。以下命令中的目录按实际情况修改：

```bash
cd /opt/src
git clone <项目仓库地址> mt-wms-rebuild
cd /opt/src/mt-wms-rebuild/WMS
```

构建应使用普通用户执行；只有安装 systemd 服务、写入 `/etc` 和 `/opt` 时使用 `sudo`。

## 3. 构建前检查

```bash
java -version
mvn --version
node --version
pnpm --version
git --version
```

期望看到 Java 17、Maven 3.9.x、Node.js 24.x 和 pnpm 10.34.5。然后执行：

```bash
cd /opt/src/mt-wms-rebuild/WMS
bash scripts/build-linux.sh
```

构建成功后生成：

```text
target/mt-wms.jar
```

该构建会执行 pnpm 锁定依赖安装、Vue/TypeScript 类型检查、前端单元测试、Vite 生产构建、Java 编译和 Java 单元测试。首次构建必须能访问 Maven 和 pnpm 依赖源；离线服务器需要提前准备 Maven 仓库与 pnpm store。

### 3.1 本地清理后需要重新下载的内容

2026 年 9 月 5 日，本地 Windows 工作区删除了以下两个可重建目录：

| 已删除目录 | 原用途 | 是否需要恢复 | 影响 |
|---|---|---|---|
| `D:\claude-code-workspace\zxj\.pnpm-store` | 工作区内遗留的 pnpm 包缓存 | 不需要手工恢复 | 当前本机 pnpm 使用 `D:\.pnpm-store\v11`；删除旧缓存不影响源码、现有 JAR 或 B 项目服务器 |
| `WMS\frontend\node_modules` | 本地前端已安装依赖 | 下次前端开发、测试或完整构建前需要恢复 | 删除后暂时不能直接运行 `pnpm dev`、前端测试或前端构建 |

恢复 `node_modules` 时，pnpm 会根据保留在仓库中的 `frontend/pnpm-lock.yaml` 重新取得全部直接依赖和传递依赖。需要恢复的主要直接依赖如下：

| 类别 | 依赖 |
|---|---|
| 前端运行依赖 | `axios`、`echarts`、`element-plus`、`pinia`、`vue`、`vue-router` |
| 构建与类型检查依赖 | `@types/node`、`@vitejs/plugin-vue`、`sass`、`typescript`、`vite`、`vue-tsc` |
| 测试依赖 | `@vue/test-utils`、`jsdom`、`vitest` |

不需要逐个安装以上软件包。在本地 Windows PowerShell 中执行：

```powershell
cd D:\claude-code-workspace\zxj\mt-wms-rebuild\WMS\frontend
pnpm install --frozen-lockfile
```

pnpm 会优先复用 `D:\.pnpm-store\v11` 中已有的包，仅从依赖源下载缓存中缺少的内容。只要 `pnpm-lock.yaml` 没有修改，恢复后的依赖版本与清理前一致。

如需直接恢复并完成整个项目的构建，也可以执行：

```powershell
cd D:\claude-code-workspace\zxj\mt-wms-rebuild\WMS
.\scripts\build.ps1
```

向 B 项目服务器部署时，不要上传本地的 `node_modules` 或 `.pnpm-store`。服务器在 `bash scripts/build-linux.sh` 过程中会根据锁文件安装自己的前端依赖，并在 Maven 构建过程中取得缺少的 Java 依赖。node4、node5、node6 已安装的 Node.js、pnpm、Java、Maven、openGauss 及其他服务不需要因为本次本地清理而重新下载。

## 4. 确认 openGauss 容器和端口

在 node4 执行：

```bash
isula ps
sudo ss -lntp | grep ':5432'
```

记录以下信息：

| 信息 | 示例 | 用途 |
|---|---|---|
| openGauss 容器名 | `opengauss` | 迁移脚本进入容器执行 `gsql` |
| 宿主机监听地址 | `127.0.0.1` 或 node4 内网地址 | 应用 JDBC 连接地址 |
| 宿主机监听端口 | `5432` | 应用 JDBC 连接端口 |
| 管理员账号 | 通常为 `omm` | 只用于建库和数据库迁移 |

如果 `ss` 查不到数据库端口，说明容器可能没有把端口发布给宿主机。不要直接重建现有数据库容器，应先确认现有 API Demo 使用的连接方式，并由服务器管理员为 MT-WMS 提供可访问的地址。

## 5. 创建 MT-WMS 独立数据库

不要使用或覆盖现有 B 项目业务数据库。请由 openGauss 管理员创建：

```sql
CREATE USER wms_app IDENTIFIED BY '替换为高强度运行密码';
CREATE DATABASE mt_wms OWNER wms_app;
```

当前数据库迁移脚本使用固定数据库名 `mt_wms` 和运行用户 `wms_app`，不要随意改名。如果已有同名对象，应先确认它是否属于本项目，禁止直接删除。

管理员账号只负责建库与迁移；应用长期运行时必须使用低权限账号 `wms_app`，不能使用 `omm`。

## 6. 配置并执行数据库迁移

先安装迁移配置模板：

```bash
cd /opt/src/mt-wms-rebuild/WMS
sudo install -d -m 0750 /etc/mt-wms
sudo install -m 0600 deploy/openeuler/mt-wms-migration.env.example \
  /etc/mt-wms/mt-wms-migration.env
sudo vi /etc/mt-wms/mt-wms-migration.env
```

修改为实际值：

```ini
CONTAINER_RUNTIME=isula
OPENGAUSS_CONTAINER_NAME=实际openGauss容器名
OPENGAUSS_GSQL_BIN=/usr/local/opengauss/bin/gsql
OPENGAUSS_LIBRARY_PATH=/usr/local/opengauss/lib:/scws/lib

WMS_DB_NAME=mt_wms
WMS_DB_ADMIN_USERNAME=omm
WMS_DB_ADMIN_PASSWORD='实际管理员密码'
```

注意：

- 该文件会被 Bash 加载，密码含空格、`#`、`$` 等字符时应使用正确的 Shell 单引号规则。
- 文件必须保持 `0600` 权限，不能提交到 Git，也不能放进应用运行配置。
- 如果容器内 `gsql` 或库文件路径与模板不同，应以实际容器为准修改。

执行迁移：

```bash
sudo WMS_MIGRATION_ENV_FILE=/etc/mt-wms/mt-wms-migration.env \
  bash scripts/migrate-opengauss.sh
```

成功时会依次显示 `V001` 至最新版本“执行成功”或“已执行，跳过”，最后输出：

```text
openGauss 数据库迁移完成：mt_wms
```

迁移脚本会在 `schema_version` 表记录版本和 SHA-256 校验值。已经执行过的 SQL 文件禁止修改；需要调整数据库结构时应新增更高版本的迁移文件。

## 7. 安装 systemd 服务

```bash
cd /opt/src/mt-wms-rebuild/WMS
sudo bash scripts/install-openeuler.sh target/mt-wms.jar
```

脚本会完成：

- 创建不可登录的 `mtwms` 系统用户；
- 安装 JAR 到 `/opt/mt-wms/mt-wms.jar`；
- 安装 `/etc/systemd/system/mt-wms.service`；
- 首次部署时创建 `/etc/mt-wms/mt-wms.env`；
- 执行 `systemctl daemon-reload`。

安装脚本不会在数据库参数填写完成前自动启动应用。

## 8. 修改应用运行环境配置

编辑：

```bash
sudo vi /etc/mt-wms/mt-wms.env
sudo chmod 0600 /etc/mt-wms/mt-wms.env
```

node4 同机部署示例：

```ini
SPRING_PROFILES_ACTIVE=prod
SERVER_PORT=18080

WMS_DB_URL=jdbc:postgresql://127.0.0.1:5432/mt_wms?currentSchema=public
WMS_DB_USERNAME=wms_app
WMS_DB_PASSWORD='实际wms_app密码'
WMS_DB_POOL_SIZE=10

WMS_FILES_DIR=/var/lib/mt-wms/files
JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75.0 -Dfile.encoding=UTF-8
```

各参数说明：

| 参数 | 是否必填 | 说明 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | 是 | 服务器必须使用 `prod`，生产模式不会启用开发账号 |
| `SERVER_PORT` | 是 | 应用监听端口，默认建议 `18080` |
| `WMS_DB_URL` | 是 | openGauss JDBC 地址；协议保持 `jdbc:postgresql` |
| `WMS_DB_USERNAME` | 是 | 固定使用低权限运行用户 `wms_app` |
| `WMS_DB_PASSWORD` | 是 | `wms_app` 的密码，不是管理员密码 |
| `WMS_DB_POOL_SIZE` | 否 | 数据库连接池上限，开发环境建议先使用 `10` |
| `WMS_FILES_DIR` | 是 | Excel 导入导出文件持久化目录 |
| `JAVA_TOOL_OPTIONS` | 否 | JVM 内存和字符集参数，可按服务器资源调整 |

如果应用部署在 node5，将 JDBC 主机改成 node4 内网地址：

```ini
WMS_DB_URL=jdbc:postgresql://<node4内网IP>:5432/mt_wms?currentSchema=public
```

不要填写 Docker Desktop 使用的主机名，也不要使用 Windows 本机 IP。配置文件遵循 systemd `EnvironmentFile` 语法，不会进行 Shell 变量展开；复杂密码建议使用单引号并优先采用不含换行和单引号的高强度随机密码。

## 9. 启动并设置开机自启

启动前确认端口没有被占用：

```bash
sudo ss -lntp | grep ':18080' || true
```

如果端口已被其他应用占用，修改 `SERVER_PORT`，并同步修改 Easegress 后端地址。

启动服务：

```bash
sudo systemctl enable --now mt-wms
sudo systemctl status mt-wms --no-pager
sudo journalctl -u mt-wms -n 100 --no-pager
```

常用运行命令：

```bash
# 启动
sudo systemctl start mt-wms

# 停止
sudo systemctl stop mt-wms

# 重启
sudo systemctl restart mt-wms

# 查看状态
sudo systemctl status mt-wms --no-pager

# 实时日志
sudo journalctl -u mt-wms -f

# 查看本次启动日志
sudo journalctl -u mt-wms -b --no-pager
```

## 10. 健康检查和验收

先在应用所在服务器执行：

```bash
cd /opt/src/mt-wms-rebuild/WMS
bash scripts/smoke-test.sh http://127.0.0.1:18080
```

必须同时通过：

| 地址 | 正常结果 | 含义 |
|---|---|---|
| `/health/live` | HTTP 200、`status=UP` | Java 进程和 Web 服务正常 |
| `/health/ready` | HTTP 200、`status=UP` | 应用已经成功连接 openGauss |

也可以手工检查：

```bash
curl -i http://127.0.0.1:18080/health/live
curl -i http://127.0.0.1:18080/health/ready
```

完整登录验收应通过最终 HTTPS 域名执行：

```bash
export WMS_SMOKE_COMPANY=default
export WMS_SMOKE_USERNAME=实际验收账号
read -rsp '请输入验收密码：' WMS_SMOKE_PASSWORD
echo
export WMS_SMOKE_PASSWORD
bash scripts/smoke-test.sh https://实际访问域名
unset WMS_SMOKE_PASSWORD
```

不要把账号密码直接写进脚本或 Shell 历史。

## 11. 配置 Easegress 入口

生产模式默认使用 Secure Session Cookie，正式访问入口必须使用 HTTPS。前端和 API 必须保持同源，避免 Session 和 CSRF Cookie 失效。

Easegress 应把同一域名下的以下请求转发到 MT-WMS：

```text
/
/assets/**
/api/**
/open/qimen/**
/health/**
```

后端地址示例：

```text
http://bpoc-node4:18080
```

代理应传递：

```text
X-Forwarded-For
X-Forwarded-Host
X-Forwarded-Proto: https
```

修改 Easegress 前应备份现有配置，避免影响当前 API1/API2 Demo。应先确认 `http://127.0.0.1:18080/health/ready` 正常，再排查网关配置。

## 12. 更新应用

更新前先按服务器 DBA 规范备份 `mt_wms` 数据库。数据库迁移通常只能向前执行，JAR 回退不能自动回退数据库结构。

```bash
cd /opt/src/mt-wms-rebuild/WMS
git pull
bash scripts/build-linux.sh

sudo cp /opt/mt-wms/mt-wms.jar /opt/mt-wms/mt-wms.jar.previous

sudo WMS_MIGRATION_ENV_FILE=/etc/mt-wms/mt-wms-migration.env \
  bash scripts/migrate-opengauss.sh

sudo bash scripts/install-openeuler.sh target/mt-wms.jar
sudo systemctl restart mt-wms
bash scripts/smoke-test.sh http://127.0.0.1:18080
```

## 13. 回退应用

只有在旧 JAR 与当前数据库结构仍兼容时才能回退：

```bash
sudo systemctl stop mt-wms
sudo mv /opt/mt-wms/mt-wms.jar.previous /opt/mt-wms/mt-wms.jar
sudo systemctl start mt-wms
sudo systemctl status mt-wms --no-pager
```

数据库回退必须使用经过验证的备份恢复方案，不能删除 `schema_version` 记录冒充回退。

## 14. 常见故障排查

### 14.1 构建提示找不到 `pnpm`

```bash
command -v pnpm
pnpm --version
```

确认服务器 PATH 中是清单已安装的 pnpm 10.34.5，不要在项目中临时升级全局 pnpm。

### 14.2 `/health/live` 正常但 `/health/ready` 返回 503

这通常表示应用已经启动，但数据库不可用。依次检查：

```bash
sudo journalctl -u mt-wms -n 200 --no-pager
sudo ss -lntp | grep ':5432'
isula ps
sudo grep -E '^(WMS_DB_URL|WMS_DB_USERNAME)=' /etc/mt-wms/mt-wms.env
```

重点检查 JDBC 主机、端口、数据库名、用户名、密码、openGauss 监听地址、客户端访问规则和防火墙。不要在终端输出数据库密码。

### 14.3 日志出现“relation does not exist”

说明数据库迁移没有完整执行，或 JDBC 连接到了错误数据库/Schema。重新核对 `WMS_DB_URL`，然后执行迁移脚本。不要手工跳过失败版本。

### 14.4 登录接口失败或浏览器反复跳回登录页

检查是否通过 HTTPS 访问，以及 Easegress 是否传递 `X-Forwarded-Proto: https`。生产模式使用 Secure Cookie，直接通过外部 HTTP 地址登录会导致 Cookie 不生效。

### 14.5 Easegress 返回 502/503

先绕过网关检查：

```bash
curl -i http://127.0.0.1:18080/health/live
curl -i http://127.0.0.1:18080/health/ready
```

本机正常时，再检查 Easegress 后端地址、端口、路由和防火墙。

### 14.6 Excel 导入导出提示文件错误

确认持久化目录存在且 systemd 创建的 `mtwms` 用户可写：

```bash
sudo ls -ld /var/lib/mt-wms /var/lib/mt-wms/files
sudo systemctl restart mt-wms
```

`mt-wms.service` 使用 `StateDirectory=mt-wms` 自动创建 `/var/lib/mt-wms`；业务子目录会由应用按需创建。

### 14.7 服务启动后立即退出

```bash
sudo systemctl status mt-wms --no-pager
sudo journalctl -u mt-wms -n 200 --no-pager
/usr/bin/java -version
sudo ls -l /opt/mt-wms/mt-wms.jar /etc/mt-wms/mt-wms.env
```

重点检查 Java 是否为 17、JAR 是否完整、环境文件是否存在，以及配置行是否符合 `KEY=VALUE` 格式。

## 15. 上线检查清单

- [ ] `bash scripts/build-linux.sh` 成功生成 `target/mt-wms.jar`。
- [ ] 已创建独立数据库 `mt_wms` 和低权限用户 `wms_app`。
- [ ] 数据库迁移从 V001 到最新版本全部成功。
- [ ] `/etc/mt-wms/mt-wms.env` 权限为 `0600`，且未使用管理员账号运行应用。
- [ ] `systemctl status mt-wms` 显示 `active (running)`。
- [ ] `/health/live` 返回 200。
- [ ] `/health/ready` 返回 200。
- [ ] Easegress 使用 HTTPS，同域转发前端和 API。
- [ ] 登录、工作台、核心业务接口和 Excel 导入导出验收通过。
- [ ] 已记录数据库备份、JAR 更新和回退方法。
